# Operation and Audit Services

## Introduction

This document defines the services belonging to the **Operation and Audit Management** subdomain of NexusMarket.

The specification requires the platform to guarantee **traceability and coordination among all participants** (Introduction) and to consolidate administrative information (OBJ-12). Every significant business action therefore generates:

* an `Operation` — the business event: who did what, when, and on which entity;
* an `AuditLog` — the detailed, immutable audit trail of that event.

The services operate exclusively with **Domain Models** and **Value Objects** and obtain external information through **Output Ports**.

Package: `application.domain.services.operation`

---

# Domain Model Context

```text
Operation
 ├── operationId     : Integer
 ├── operationType   : OperationType
 ├── executionDate   : LocalDateTime
 ├── performedBy     : User
 └── affectedEntity  : TraceableEntity?     (null for actions on persons: buyers, sellers, users)

AuditLog
 ├── auditId         : String
 ├── operationType   : OperationType
 ├── operationDate   : LocalDateTime
 ├── performedBy     : User
 ├── userRole        : SystemRole           (role at the moment of the action)
 ├── affectedEntity  : TraceableEntity?
 └── details         : Map<String,Object>   (previous/new status, quantities, amounts, ...)
```

`TraceableEntity` is the common base of `Warehouse`, `Product`, `ProductVariant`, `InventoryItem`, `Order`, `Invoice`, `Shipment`, `ReturnRequest` and `Refund` (equivalent to `BankingProduct` in the reference project).

---

# Purpose of Operations

Operations answer "which business actions happened": they feed the operational follow-up of supervisors and administrators and allow searching by user, entity or type.

# Purpose of Audit Logs

Audit logs preserve **how** the action happened (the `details` map) and the role of the user at that moment. They are immutable and are stored in MongoDB.

---

# Service Design Principles

## Domain Model Parameters

Incorrect:

```java
registerOperation(String type, Integer userId, String entityId);
```

Correct:

```java
registerOperationAndAudit(User user, OperationType type, TraceableEntity affectedEntity, Map<String,Object> details);
```

## Single entry point

Business services never call `RegisterOperationService` or `RegisterAuditLogService` directly. They always call **`RegisterOperationAndAuditService`**, which creates both records consistently.

## Immutability

Operations and audit logs are never updated or deleted. Their ports have no `update` or `delete` methods.

# 1. Register Operation and Audit

| Item          | Value |
| ------------- | ----- |
| Class         | `RegisterOperationAndAuditService` |
| Methods       | `void execute(User user, OperationType type, TraceableEntity affectedEntity, Map<String,Object> auditDetails)`<br>`void execute(Operation operation, Map<String,Object> auditDetails)` |
| Invoked by    | Every auditable business service |
| Internal services | `RegisterOperationService`, `RegisterAuditLogService` |

## Processing

```text
Operation(type, executionDate = now, performedBy = user, affectedEntity) ──► RegisterOperationService
AuditLog(operationType, operationDate = now, performedBy, userRole = performedBy.role,
         affectedEntity, details)                                         ──► RegisterAuditLogService
```

## Rule

It must be called **after** the business change has been persisted, so that `affectedEntity.identifier` is already assigned.

# 4. Consult Operations

| Item          | Value |
| ------------- | ----- |
| Class         | `ConsultOperationsService` |
| Methods       | `List<Operation> executeByUser(User requestingUser, User targetUser)`<br>`List<Operation> executeByEntity(User requestingUser, TraceableEntity entity)`<br>`List<Operation> executeByType(User requestingUser, Operation operation)` |
| Authorization | `AuthorizeAdministrativeConsultationService` (ADMINISTRATOR, SUPERVISOR) |
| Output Ports  | `OperationRepositoryPort` |

## Description

Retrieves operations performed by a user, affecting an entity, or of a given `operationType` (`operation.operationType` is the filter).

For `executeByEntity` the input adapter builds the concrete `TraceableEntity` subclass (e.g. `Order` with its `identifier`) from the entity type and identifier received in the request.

## Exceptions

| Exception | Condition |
| --------- | --------- |
| `UnauthorizedOperationException` | Not an active administrator or supervisor. |

# Persistence

| Record      | Storage | Adapter |
| ----------- | ------- | ------- |
| `Operation` | MySQL (`operation` table) | `OperationMySqlAdapter` |
| `AuditLog`  | MongoDB (`audit_logs` collection) | `AuditLogMongoAdapter` |

The audit log is written to MongoDB and is therefore **not** part of the MySQL transaction of the use case. If the business transaction rolls back after the audit log was written, an orphan audit entry may remain. Acceptable options, from simplest to strictest:

1. Accept it (audit of attempted actions).
2. Write audit logs after commit (`TransactionSynchronization.afterCommit` in the Mongo adapter).
